<p>Every Bicep module author faces the same chore as anyone else:</p><p><em>Keeping a README file in sync with all parameters, outputs, and types the compiler already knows everything about.</em></p><p>I've been there myself. When <code>bicep local deploy</code> released, I published <a href="https://github.com/Gijsreyn/bicep-local-docgen"><code>bicep-local-docgen</code></a> to take some of the heavy lifting away from Bicep's own compiler.</p><p>But there's finally some light at the end of the tunnel. With the following <a href="https://github.com/Azure/bicep/pull/20183">pull request</a> by one of the members of the AVM project, it seems that the Bicep CLI gets its own command: <code>bicep docs generate</code>.</p><p>In this post, I'll walk you through the five-year history behind that command, the tooling the community built to fill the gap, and why the AVM project finally pushed documentation generation into the Bicep CLI itself. Then, we go to the actual command itself.</p><h2 id="five-years-of-asking">Five years of asking</h2><p>The idea to get native support for documentation generation is not new. Back in October 2021, Ben Wilkinson opened <a href="https://github.com/Azure/bicep/issues/4935">4395</a>, "Auto generated documentation e.g. Markdown and schema", asking for exactly this: a built-in way to turn a Bicep module into readable documentation. Nearly five years later, that issue was still open, parked on the team's backlog while thumbs-ups and workarounds accumulated underneath it.</p><p>The thread also captured why it stayed open so long. Bicep maintainer Anthony Martin observed early on that the hard part isn't producing Markdown; it's that everyone wants their documentation in some different way. A built-in generator would either be too opinionated to be useful, or collapse under a pile of formatting options.</p><p>But it was Jared Holgate, one of the core maintainers of AVM, who broke the deadlock. Jared opened a proposal, which led to a design document: <a href="https://github.com/Azure/bicep-reps/blob/main/active/0025-module-documentation-generation.md">REP 0025, "Module documentation generation commands"</a>. And as you'll soon learn, it answers a lot of the formatting objections.</p><h2 id="what-the-community-built-in-the-meantime">What the community built in the meantime</h2><p>While the issue sat open, the community didn't sit still either. It built its own tooling, so it's good to look back at the tools that fall roughly into three generations.</p><p>The first generation worked around the problem by not parsing Bicep at all. This was <a href="https://github.com/Azure/PSDocs.Azure">PSDocs.Azure</a>. PSDocs.Azure consumed ARM template JSON, so the recipe was straightforward in most blog posts: run <code>bicep build</code> first, then hand the compiled output to PSDocs. It worked, but anything that didn't survive compilation was lost along the way, and <a href="https://github.com/Azure/PSDocs.Azure/issues/106">native Bicep support</a>, requested back in 2021, never arrived.</p><blockquote>
<p>[!NOTE]<br>
The latest stable release dates from May 2021.</p>
</blockquote>
<p>A second tool targeted Bicep more directly and was developed by Christos Galanopoulos. It was fully written as Go CLI and was simply named <a href="https://github.com/christosgalano/bicep-docs">bicep-docs</a>. It's still an active project maintained today and takes more of a hybrid approach: it compiles your file to ARM JSON, but additionally scans the Bicep source for the things compilation obscures. Think about declarations and decorators.</p><p>The PSBicep module went one step further and embedded the <a href="https://github.com/PSBicep/PSBicep/blob/main/Docs/Bicep/New-BicepMarkdownDocumentation.md"><code>New-BicepMarkdownDocumentation</code></a> cmdlet to the actual Bicep .NET assembly. This way, it parses your file with the real compiler (and even in-process as well). </p><p>My own <a href="https://www.nuget.org/packages/bicep-local-docgen"><code>bicep-local-docgen</code></a> sits in a different lane and doesn't document Bicep modules at all. Instead, it documents Bicep Local Deploy extensions by reading the C# resource models an extension author writes and generating Markdown reference documentation from them. Just complementary rather than competing. But it taught me the same lesson every tool in this list learned the hard way: documentation tooling really wants to live next to the thing it documents.</p><blockquote>
<p>[!NOTE]<br>
There are other abandoned attempts too. Joachim Dalen created a <a href="https://github.com/joachimdalen/bicepdocs">C# generator built on Bicep's own libraries</a>, but was archived early in 2025.</p>
</blockquote>
<h2 id="avm-the-straw-that-broke-the-camels-back">AVM: the straw that broke the camel's back</h2><p>If there's any Bicep project out there that knows the pain at such a scale, it's the Azure Verified Modules (AVM) project. The AVM specification even mandates it in a <a href="https://azure.github.io/Azure-Verified-Modules/spec/BCPNFR2/">specification document</a> to produce proper documentation. It specifies that every module produces a <code>README.md</code> file. </p><p>To make it easier for authors, the AVM created its own tooling, and oh boy, this PowerShell script has grown to become a beast, which is roughly 2400 lines. That tool is known as <a href="https://github.com/Azure/bicep-registry-modules/blob/main/utilities/pipelines/sharedScripts/Set-ModuleReadMe.ps1"><code>Set-ModuleReadMe.ps1</code></a>. It parses the ARM JSON, and rebuilds the README section by section. It even calls out to Microsoft Learn at generation time to validate reference links, which means generating documentation requires an internet connection.</p><p>The script works. I think it documents more than 570 modules in the public registry today. But it's held together by conventions. Parameters land in the <em>Required </em>or <em>Optional </em>based on the prefix of their description text. Hand-written content only survives in a handful of locations. And every time the Bicep language grows a new feature, someone has to teach the script about it from the outside.</p><p>The design proposal states the motivation bluntly: the AVM script is "non-trivial PowerShell that has to be maintained outside of the Bicep compiler, despite depending on Bicep's compiled output."</p><p>And here's the kicker: the pull request's author, Jared Holgate, is a core team member of the AVM project, and <a href="https://github.com/Azure/bicep-reps/blob/main/active/0025-module-documentation-generation.md">REP 0025</a> explicitly names <code>Set-ModuleReadme.ps1</code> as the prior art the new feature is "intended to replace for most consumers."</p><p>This isn't the Bicep team guessing what a docs generation should look like. It comes directly from the team with the largest generated-docs estate in the ecosystem, moving that into the compiler itself.</p><h2 id="meet-bicep-docs">Meet <code>bicep docs</code></h2><p>The pull request is merged into main and introduces something the Bicep CLI has never had before: a command <em>group</em>.</p><p>Instead of a flat <code>bicep generate-docs</code>, you get a <code>docs</code> verb with two subcommands underneath. It's a deliberate choice in the design document because it leaves room for future additions like <code>docs validate</code> or <code>docs-init-template</code>.</p><pre><code class="language-powershell"># Generate a README.md next to the module
bicep docs generate ./main.bicep&#10;
# Bulk generation across a module tree
bicep docs generate --pattern './modules/**/main.bicep'&#10;
# Render to stdout without writing anything
bicep docs output ./main.bicep</code></pre><p><code>docs generate</code> writes a <code>README.md</code> next to your module (the file name is configurable with <code>--output-file</code>), and the <code>--pattern</code> variant follows the same glob convention that <code>build</code>, <code>format</code>, and <code>lint</code> already use for bulk operations. <code>docs output</code> renders the same documentation to stdout without touching disk.</p><p>So what ends up in the generated README file? Rather than describing the output here, let me show it. I wrote a small storage account module that exercises the features I care about, like file-level metadata, decorated parameters, and a discriminated union type:</p><pre><code class="language-bicep">metadata name = 'Storage Account'
metadata description = 'Deploys an Azure Storage Account with optional blob containers.'&#10;
@description('The name of the storage account. Must be globally unique.')
@minLength(3)
@maxLength(24)
param name string&#10;
@description('The storage account SKU.')
@allowed(['Standard_LRS', 'Standard_GRS', 'Premium_LRS'])
param skuName string = 'Standard_LRS'&#10;
@description('Network access configuration for the storage account.')
param networkAccess networkAccessType = { kind: 'public' }&#10;
@description('Defines how the storage account can be reached.')
@discriminator('kind')
type networkAccessType = publicAccess | restrictedAccess&#10;
@description('Publicly accessible from all networks.')
type publicAccess = {
  kind: 'public'
}&#10;
@description('Restricted to a set of allowed CIDR ranges.')
type restrictedAccess = {
  kind: 'restricted'&#10;
  @description('The CIDR ranges allowed to access the storage account.')
  allowedCidrs: string[]
}&#10;
// ...plus the storage resources, a location and containers parameter, and two outputs</code></pre><p>Next to it sits an <code>examples/basic/main.bicep</code> showing how to consume the module (sounds familiar, right?). Running the <code>bicep docs generate main.bicep</code> and the generated README opens with the title and description from the <code>metadata</code> statements, a navigation block, a table of the resource types, the module deploys, and my example file rendered as a numbered, ready-to-copy usage example (discovered by the <code>examples/</code> folder).  </p><p>And here's the part where all the decorators you've been adding finally pay off:</p><pre><code class="language-markdown">## Parameters&#10;
| Name | Type | Required | Description |
| :-- | :-- | :-- | :-- |
| `containers` | `array` | No | Blob containers to create in the storage account. |
| `location` | `string` | No | The Azure region to deploy to. |
| `name` | `string` | Yes | The name of the storage account. Must be globally unique. |
| `networkAccess` | `object` | No | Network access configuration for the storage account. |
| `skuName` | `string` | No | The storage account SKU. |&#10;
### `networkAccess`&#10;
- Default value: `{ kind: 'public' }`&#10;
- Discriminator: `kind`
  - `public`:
    - `kind` (`string`), required
      - Allowed values: `public`
  - `restricted`:
    - `allowedCidrs` (`array`), required: The CIDR ranges allowed to access the storage account.
    - `kind` (`string`), required
      - Allowed values: `restricted`</code></pre><p>Every parameter gets a detail section with its default value, allowed values, and length or value constraints (<code>name</code> shows its min and max length; secure parameters render as <code>securestring</code>). But the <code>networkAccess</code> breakdown is my favorite part: the discriminated union is expanded recursively, case by case, with required flags and descriptions. You don't have to guess what shape it has through the source itself.</p><p>Stepping a bit back. Remember Anthony Martin's objection that everyone wants their documentation formatted differently? The answer turns out to be templates. The built-in output is a sensible default, but pass <code>--template-file</code> with your own <a href="https://github.com/scriban/scriban">Scriban template</a>, and you can reshape the entire document. And if you want to inject values from the outside, use <code>--custom-template-value</code>.</p><p>The command is going to be shipped as an experimental feature. But don't worry for this one, you don't have to turn on any flag in your <code>bicepconfig.json</code>. The full command and template references lives in <a href="https://github.com/Azure/bicep/blob/main/docs/experimental/docs-commands.md"><code>docs/experimental/docs-commands.md</code></a>.</p><h2 id="what-this-means">What this means</h2><p>The real differentiator of every tool from the middle of the post comes down to one thing: <em>architectural</em>.</p><p><code>bicep docs</code> reads the compiler's semantic model, not the compiled JSON. Everything the community had to do is reverse-engineer from the outside. Now, every user-defined type, decorator, and exported function just flows into the documentation for free as the language (Bicep) evolves. A module with compile errors is refused outright rather than half-documented. And the output is deterministic: the same module with the same template produces the same README, byte for byte.</p><p>That claim on determinism isn't theoretical. If you look at the original PR, Jarod ran the tool across the entire public module registry. Those were 573 AVM module entry points in about seven and a half minutes, with all the READMEs matching the checked-in ones (at least, it was 572, as there was a single failure a module with compile errors). </p><p>So where does that leave you? If you author modules, the wrapper scripts, or the other tooling that you've used can now have a retirement date. If you contribute to AVM, so does the 2400-line PowerShell script. And lastly, this one is even better. The engine is also exposed over JSON-RPC and through the <code>Azure.Bicep.RpcClient</code> .NET package, so a pipeline can document hundreds of modules in a single process instead of shelling out per file.</p><p>One honest caveat before you wire anything into a production pipeline. Even though the pull request has been merged to main, it's still labeled as experimental. It's now your time to give feedback!</p>
