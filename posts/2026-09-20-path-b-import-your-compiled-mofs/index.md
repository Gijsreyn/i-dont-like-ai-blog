<p>Path A assumed you have (or can reconstruct) the original <code>Configuration</code> scripts. Sometimes you can't.</p>
<p>Pull servers accumulate compiled MOFs whose source scripts are long gone, or that were generated by a build system nobody runs anymore, or that came from a team that was reorganized out of existence two years ago. For those, an import extension turns from a neat trick into a genuine rescue tool.</p>
<h2 id="how-import-extensions-work">How import extensions work</h2>
<p>Microsoft DSC extensions have three capabilities: <strong>secret</strong>, <strong>discover</strong>, and <strong>import</strong>. An import extension converts configuration files from other formats into DSC configuration documents.</p>
<p>The MOF import extension declares which file extensions it handles in its manifest, <code>moftodsc.dsc.extension.json</code>:</p>
<pre><code class="language-json">{
  "$schema": "https://aka.ms/dsc/schemas/v3/bundled/extension/manifest.json",
  "type": "DSC.Transitional/MofToDsc",
  "version": "0.1.0",
  "description": "Converts MOF configuration files to valid DSC configuration documents.",
  "import": {
    "fileExtensions": ["mof"],
    "executable": "pwsh",
    "args": [
      "-NoLogo",
      "-NonInteractive",
      "-NoProfile",
      "-Command",
      "./convert-mof.ps1",
      {
        "fileArg": "-Path"
      }
    ]
  }
}
</code></pre>
<p>Two properties do the work:</p>
<ul>
<li><strong><code>fileExtensions: ["mof"]</code></strong> makes any <code>dsc config</code> command that receives a <code>.mof</code> file route it through this extension first.</li>
<li><strong><code>fileArg</code></strong> marks where DSC inserts the absolute path of the file being imported, so the wrapper script receives <code>-Path C:\...\localhost.mof</code>.</li>
</ul>
<p>The wrapper script is tiny. It delegates to <code>Convert-MofToDsc</code> from the <code>DSCSchemaBuilder</code> module:</p>
<pre><code class="language-powershell"># convert-mof.ps1
[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [string]$Path
)&#10;
$ErrorActionPreference = 'Stop'&#10;
Convert-MofToDsc -Path $Path
</code></pre>
<blockquote>
<p>[!IMPORTANT]<br>
DSC finds the extension when both files sit in the folder that contains the <code>dsc</code> executable. Save <code>moftodsc.dsc.extension.json</code> and <code>convert-mof.ps1</code> side by side in that folder, which this command prints:</p>
<pre><code class="language-powershell">Split-Path (Get-Command dsc).Path
</code></pre>
<p>The manifest calls <code>./convert-mof.ps1</code> by a relative path, so the script has to sit beside the manifest. <a href="/courses/migrating-from-powershell-dsc/convert-a-mof-file/">Unit 5</a> walks through copying the files there and confirming discovery with <code>dsc extension list</code>.</p>
</blockquote>
<p><code>Convert-MofToDsc</code> parses the MOF and writes a valid configuration document as JSON to stdout. That's the entire contract an import extension must fulfill.</p>
<blockquote>
<p>[!NOTE]<br>
<code>Convert-MofToDsc</code> ships in the <a href="https://www.powershellgallery.com/packages/DscSchemaBuilder"><code>DSCSchemaBuilder</code></a> module on the PowerShell Gallery. The module requires PowerShell 7.5 or later, so install it from a PowerShell 7 session:</p>
<pre><code class="language-powershell">Install-PSResource -Name DSCSchemaBuilder
</code></pre>
<p>The extension invokes <code>pwsh</code>, so a copy installed for Windows PowerShell 5.1 isn't visible to it.</p>
</blockquote>
<p><img src="https://storage.ghost.io/c/dd/64/dd64ba9d-7bdd-441e-bb5f-13f8be709814/content/images/2026/10/mof-import-flow.png" alt="Figure 1: The engine never learns the input was MOF. The extension translates before the document reaches it." loading="lazy"></p>
<h2 id="translate-on-the-fly">Translate on the fly</h2>
<p>With the extension installed, this just works:</p>
<pre><code class="language-powershell">dsc config test --file .\output\localhost.mof
</code></pre>
<p>That's remarkable when you think about it. A file compiled by Windows PowerShell in 2019 is being evaluated by a Rust engine that never heard of the LCM, because an extension translated between the two worlds at invocation time.</p>
<p>Add <code>-l debug</code> to watch the selection happen:</p>
<pre><code class="language-powershell">dsc -l debug config test --file .\output\localhost.mof
</code></pre>
<p>The trace shows the <code>.mof</code> extension matching <code>DSC.Transitional/MofToDsc</code>, the <code>pwsh</code> invocation, and the JSON coming back.</p>
<h2 id="but-dont-stop-there">But don't stop there</h2>
<p>For migration purposes, on-the-fly translation is a <strong>diagnostic tool, not a destination</strong>. You don't want <code>.mof</code> files living in your repository forever with a translation shim in front of them. That's two artifacts and a dependency where one artifact would do.</p>
<p>Run the conversion once and keep the result:</p>
<pre><code class="language-powershell">Convert-MofToDsc -Path .\output\localhost.mof |
    Out-File .\webserver-imported.dsc.config.json
</code></pre>
<blockquote>
<p>[!TIP]<br>
Prefer YAML for your documents? Chain the conversion:</p>
<pre><code class="language-powershell">Convert-MofToDsc -Path .\output\localhost.mof |
    ConvertFrom-Json |
    ConvertTo-Yaml |
    Out-File .\webserver-imported.dsc.config.yaml
</code></pre>
<p><code>ConvertTo-Yaml</code> comes from the <code>powershell-yaml</code> module or <code>yayaml</code> on the PowerShell Gallery.</p>
</blockquote>
<p>The output is a configuration document in JSON with:</p>
<ul>
<li>Each MOF instance mapped to an adapted resource (<code>PSDesiredStateConfiguration/File</code> and so on)</li>
<li><code>DependsOn</code> entries rewritten as <code>resourceId()</code> references</li>
<li>Compilation metadata such as <code>SourceInfo</code> stripped away</li>
</ul>
<p>From here you're back on Path A: the document references legacy resources through the adapter, and you refine it like any hand-written document.</p>
<h2 id="review-checklist-the-four-blind-spots">Review checklist: the four blind spots</h2>
<p>Mechanical conversion has known limits. Review every imported document against these four points before committing it.</p>
<h3 id="1-credentials-are-gone-deliberately">1. Credentials are gone, deliberately</h3>
<p>MOF files stored <code>MSFT_Credential</code> blocks, either in plaintext or encrypted with a certificate. Importers can't and shouldn't translate them.</p>
<p>Re-model them as <code>secureString</code> parameters. Unit 5 of Module 3 covers where the values come from.</p>
<h3 id="2-node-names-vanish">2. Node names vanish</h3>
<p>A MOF is compiled per node, while a configuration document is node-agnostic. If you had per-node MOF variations, extract the differences into parameters and use one document with per-node parameter files.</p>
<p>This is usually the biggest win hiding in an import: forty MOFs that differ in three values become one document and forty small parameter files. More often you end up with four parameter files, once you notice that thirty-six of the nodes were identical.</p>
<h3 id="3-composite-resources-arrive-flattened">3. Composite resources arrive flattened</h3>
<p>The MOF compiler already expanded composites into their member resources, so the import gives you the flattened version. That's <em>correct</em> in the sense that it produces the same end state, but it loses the abstraction.</p>
<p>If the grouping mattered, rebuild it with <code>Microsoft.DSC/Include</code> composing multiple documents.</p>
<h3 id="4-ordering-became-explicit">4. Ordering became explicit</h3>
<p>Anything the LCM ran in implicit document order now needs real <code>dependsOn</code> entries. The importer preserves explicit <code>DependsOn</code> values faithfully, but implicit ordering assumptions are yours to rediscover. They stay invisible until something runs in the wrong order on a machine that isn't yours.</p>
<blockquote>
<p>[!IMPORTANT]<br>
Convert one MOF, run <code>dsc config test</code> against a machine that the LCM currently manages, and compare. In-desired-state results across the board mean the translation is faithful. This is the cheapest possible validation of the entire import path, and it requires no changes to the running system.</p>
</blockquote>
<h2 id="scale-it-without-a-big-bang">Scale it without a big bang</h2>
<p>Converting four hundred MOFs in one weekend produces four hundred unreviewed documents, which is worse than having four hundred MOFs. Convert <strong>per service</strong>:</p>
<ol>
<li>Pick one service with a handful of nodes.</li>
<li>Convert its MOFs, collapse the per-node differences into parameters.</li>
<li>Run <code>dsc config test</code> against every live node in that service.</li>
<li>Commit the document, retire the MOFs, and move to the next service.</li>
</ol>
<p>Each converted document earns its way into the repository by proving it agrees with a running machine.</p>
