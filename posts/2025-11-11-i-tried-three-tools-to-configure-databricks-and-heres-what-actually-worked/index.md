<p>For weeks, we've been debating about PowerShell scripts, Terraform configs, and figured Bicep templates didn't entirely work for managing our Databricks workspace.</p><p>Each tool promised to be "the one". Then Bicep extensions arrived, and everything changed.</p><p>Here's what I learned about choosing the right tool for configuring (Azure) Databricks, and why the answer isn't what you'd expect.</p><h2 id="the-problem-i-didnt-know-i-had">The problem I didn't know I had </h2><p>It started innocently enough. We had been focusing mainly on Azure infrastructure. We declared the infrastructure using Azure Bicep. After locking down the environment, we reached a point where we had a Databricks workspace and needed some configuration.</p><p>That's when we hit the wall.</p><p>Bicep could create the Databricks workspace instance – that became easy. But configuring what's <em>inside </em>the workspace? Catalogs, schemas, clusters, credentials? That required something else entirely. The Databricks API was separate from Azure Resource Manager, and Bicep didn't speak that language.</p><p>So we did what everyone does: we cobbled together a solution.</p><p>"Just run this PowerShell script with a module. Oh, wait, but first you need to set these environment variables. And make sure you're using the right API version. Actually, let me just do it myself."</p><p>It worked, but it felt wrong. We had beautiful, declarative Bicep templates for our Azure infrastructure. And then we had... scripts. Scripts that needed documentation. Scripts that broke when APIs changed. Scripts that only two people really understood.</p><p>I thought the solution was obvious: we just needed "proper" infrastructure-as-code for the Databricks configuration. So I did what any sensible person would do: I started researching.</p><p>And that's when I discovered something worse than no automation.</p><p>I discovered <em>choice paralysis</em>.</p><p>Everyone had an opinion. PowerShell folks swore by the flexibility and direct API access. Terraform people pointed to the mature Databricks provider and massive community support. And Bicep? Well, we already knew Bicep couldn't do it. Or so we thought.</p><p>The problem wasn't just choosing a tool. It was that we'd already invested in Bicep for Azure, and now we needed to add another tool just to configure what's inside our Databricks workspaces. Our infrastructure-as-code story was about to become infrastructure-as-multiple-tools.</p><p>But I had to make a decision. So I did what I had to do: I tried all three.</p><h2 id="the-terraform-debate">The Terraform debate</h2><p>Before diving into anything, we had to address the elephant in the room: Terraform.</p><p>The team had mixed feelings. Some had used it before and loved it. Others had heard the horror stories about state files and drift. I sat down and made a list.</p><p><strong>The case FOR Terraform:</strong></p><ul><li>Mature Databricks provider with hundreds of resources</li><li>Declarative approach — just describe what you want</li><li>Massive community and Stack Overflow support</li><li>Works across cloud providers if we ever need that</li><li>Proven at scale in many organizations</li></ul><p><strong>The case AGAINST Terraform:</strong></p><ul><li>We'd need to manage state files (where? how? who has access?)</li><li>Yet another tool to learn and maintain</li><li>Another language (HCL) that not everyone on the team knew</li><li>Drift management when people inevitably click around in the UI</li><li>We're already using Bicep for Azure — now we'd have two IaC tools</li></ul><p>The arguments went back and forth. "But everyone uses Terraform!" versus "Do we really need all that complexity?" Some pointed to the mature provider. Others worried about the learning curve and operational overhead.</p><p>In the end, we decided to do a quick exploration, but with skepticism. If we were going to add Terraform to our stack, it needed to be significantly better than the alternatives. Not just "industry standard" — actually better for our specific situation.</p><p>Meanwhile, I suggested: "Why don't we just start with PowerShell? It's simple, we already know it, and we can always migrate later."</p><p>That seemed reasonable. So PowerShell it was. At least to start.</p><h2 id="powershell-where-we-started">PowerShell: Where we started </h2><p>PowerShell felt like home. I'd been writing PowerShell for years. The Databricks API was well-documented. How hard could it be?</p><p>Turns out, not hard at all. That was the problem.</p><p>I started with a simple script to create clusters. Then I needed to manage secrets. Then Unity Catalog. Before I knew it, I had a folder full of scripts, each one slightly different from the last. Some used environment variables, others took parameters. Some had error handling, others... didn't.</p><p>The worst part? It worked. Really well, actually.</p><p>PowerShell gave me complete control. When I needed to do something weird, I could easily leverage <a href="https://github.com/gbrueckl/Databricks.API.PowerShell/blob/a5debb8c559db7d36c04db71b6f54ac51789bb09/Modules/DatabricksPS/Public/General.ps1#L1"><code>Invoke-DatabricksApiRequest</code></a>. The API client was straightforward, and with easy commands available to me, it worked great.</p><p>But here's what nobody tells you about PowerShell for infrastructure management: you're not building automation, you're building a framework.</p><p>Every script needed error handling. Every script required logging. Every script needed some way to handle state — "did I already create this thing?" Parameters need validation. Some operations needed retries. And don't even get me started on trying to make these scripts idempotent.</p><p>Three months in, I realized I'd spent more time building infrastructure around my PowerShell scripts than I had actually managing infrastructure.</p><h3 id="when-powershell-actually-makes-sense">When PowerShell actually makes sense</h3><p>Don't get me wrong. PowerShell isn't the real problem. It's perfect for certain things:</p><ul><li><strong>One-off operations</strong>: Need to bulk-update cluster configurations? PowerShell is your friend.</li><li><strong>Debugging</strong>: When something's broken and you need to poke around the API manually, PowerShell's interactivity is unbeatable.</li><li><strong>Complex workflows</strong>: When you need actual programming logic (not just resource declarations), PowerShell shines.</li></ul><p>But for managing infrastructure state over time, especially around permissions? I was fighting an uphill battle, and I knew it.</p><h2 id="terraform-the-industry-standard-that-almost-broke-us">Terraform: The industry standard that almost broke us</h2><p>After my PowerShell adventure, Terraform seemed like the obvious next step. Everyone uses Terraform, right? There's a reason it's the industry standard.</p><p>The Databricks provider was mature. Hundreds of resources supported. Thousands of questions answered on Stack Overflow. This was going to be easy.</p><p>It was not easy.</p><p>Look, Terraform is brilliant. The declarative approach makes sense. The state management is solid. The provider ecosystem is unmatched. But somewhere between <code>terraform init</code> and my fifth state file conflict, I started to wonder if I'd made a mistake.</p><p>Here's what happened: I'd define a cluster in HCL. Run <code>terraform apply</code>. Great, cluster created. Then someone would modify that cluster in the Databricks UI (it happens). Next time I ran <code>terraform plan</code>, it wanted to destroy and recreate everything.</p><p>"Just use <code>terraform import</code>," they said. So I did. Except now my state file had drifted from my code. And my code was getting complicated — workspaces, modules, remote state. I was spending more time managing Terraform than managing Databricks.</p><p>The breaking point came on a late afternoon. I'd been debugging a state conflict for four hours. Four hours. The cluster existed. Terraform thought it didn't. Or maybe it did? The state said one thing, but <code>terraform refresh</code> said another.</p><p>I fixed it eventually. But as I sat there, staring at my state file in VS Code, I realized I was optimizing for Terraform, not for Databricks.</p><h3 id="where-terraform-is-actually-perfect">Where Terraform is actually perfect</h3><p>Here's the thing. Terraform certainly didn't fail me. I just wasn't the right user for it. </p><p>Terraform is phenomenal when:</p><ul><li><strong>You're managing multi-cloud infrastructure</strong>: AWS + Azure + GCP? Terraform has you covered.</li><li><strong>You have a dedicated platform team</strong>: People who eat, sleep, and breathe Terraform.</li><li><strong>Complex dependencies matter</strong>: When Resource B depends on Resource A's output, and Resource C needs both.</li><li><strong>You need that mature ecosystem</strong>: Want to manage Databricks, Snowflake, and GitHub in one place? Terraform's probably your only option.</li></ul><p>But I wasn't doing any of that. I was managing Databricks on Azure. That's it. Just Azure.</p><p>And that's when the experience around Bicep extensions changed everything.</p><h2 id="bicep-the-tool-i-dismissed">Bicep: The tool I dismissed</h2><p>I'll be honest: I'd written off Bicep completely.</p><p>"Bicep only does Azure resources," I thought. "Databricks isn't really an Azure resource. Sure, I can create the workspace, but I can't configure anything inside it."</p><p>This was true until it wasn't.</p><p>Bicep extensions changed everything. Suddenly, Bicep wasn't just for Azure Resource Manager. It could be extended to manage anything with an API. And someone had built a Databricks extension.</p><p>I was hesitant. I'd already invested time in PowerShell and Terraform. Did I really want to learn another tool and probably another programming language?</p><p>But here's what got me: the simplicity.</p><pre><code class="language-bicep">targetScope = 'local'&#10;
param workspaceUrl string&#10;
extension databricks with {
  workspaceUrl: workspaceUrl
}&#10;
resource cluster 'Cluster' = {
  clusterName: 'analytics-cluster'
  sparkVersion: '13.3.x-scala2.12'
  nodeTypeId: 'Standard_DS3_v2'
  numWorkers: 2
  autoterminationMinutes: 120
}</code></pre><p>That's it. No state files to manage. Just declare what you want, and Bicep handles the rest.</p><p>And because it's Bicep, I got all the good stuff for free:</p><ul><li><strong>Type safety</strong>: Typo a property name? Bicep catches it before deployment.</li><li><strong>IntelliSense</strong>: All the available properties, right there in VS Code.</li><li><strong>Native Azure integration</strong>: Managing the Databricks workspace resource and the internal configuration in the same language.</li></ul><h3 id="my-first-real-deployment">My first real deployment</h3><p>I decided to test it on something real: migrating our Unity Catalog configuration to Bicep.</p><p>I expected pain. I'd spent weeks getting this right in Terraform, and before that, even longer with PowerShell scripts.</p><p>It took me an afternoon to hook Bicep into Databricks' API.</p><p>One Bicep file. Catalogs, schemas, external locations, credentials — everything. And because Bicep is declarative, I didn't need to worry about order of operations. It just figured it out.</p><p>The best part? When I handed this off to my team, they got it immediately. No Terraform state to explain. No PowerShell framework to document. Just Bicep templates that looked like the Azure ARM templates they already knew.</p><h2 id="the-real-question-what-are-you-actually-trying-to-do">The real question: What are you actually trying to do?</h2><p>After months of using all three tools, I realized something important: I'd been asking the wrong question.</p><p>The question wasn't "which tool is best?" The question was "what problem am I solving?"</p><p>For me, the problem was simple: manage Databricks configuration on Azure in a way that my team could understand and maintain.</p><p>For you? The problem might be completely different.</p><p>Here's the decision matrix I use now:</p><p><strong>Reach for PowerShell when</strong>:</p><ul><li>You need one-off operations or scripts</li><li>You're debugging or exploring the API</li><li>You need actual programming logic and control flow</li><li>You already have a library of PowerShell scripts</li></ul><p><strong>Reach for Terraform when</strong>:</p><ul><li>You're managing multiple cloud providers</li><li>You have complex cross-resource dependencies</li><li>You need to manage Databricks alongside other non-Azure services</li><li>You have a team that already knows Terraform</li></ul><p><strong>Reach for Bicep (with extensions) when</strong>:</p><ul><li>You're primarily on Azure</li><li>You want type safety and IntelliSense</li><li>Your team already knows Azure and Bicep templates</li><li>You can invest time in extensions</li></ul><p>The uncomfortable truth? There's no universally correct answer. The "best" tool is the one that fits your actual situation, not the one with the most GitHub stars.</p><h2 id="what-i-wish-id-known-earlier-on">What I wish I'd known earlier on</h2><p>Looking back, here's what would have saved me weeks of frustration:</p><p><strong>Start simple.</strong> I wasted time building complex PowerShell frameworks when I could have switched to DSC. Don't add complexity until you actually need it.</p><p><strong>Ship first, optimize later.</strong> My Terraform setup was over-engineered from day one. Modules, workspaces, remote state — all before I'd deployed a single cluster to production.</p><p><strong>Master one tool deeply before adding another. </strong>I was bouncing between three tools, never really learning any of them properly. Pick one, get good at it, then evaluate if you actually need something different.</p><p><strong>Your team's knowledge matters more than the tool's capabilities.</strong> A tool your team can confidently use is better than a "better" tool they don't understand.</p><p>The biggest lesson? <strong>Stop debating and start deploying.</strong> I spent probably 40 hours researching and testing tools. In hindsight, I could have picked any of them and been productive.</p><h2 id="my-recommendation-with-caveats">My recommendation (with caveats)</h2><p>So what do I actually use now?</p><p><strong>PowerShell for 90-95% of my Databricks work.</strong> Yes, even after trying all three tools. It's not perfect, but it's pragmatic. I've streamlined my scripts, built some reusable functions, and accepted that sometimes "good enough" beats "theoretically optimal." The team knows it, it works, and we can ship.</p><p><strong>Bicep extensions for the remaining 5-10%.</strong> Here's the thing: Bicep extensions for Databricks aren't GA (generally available) yet. That matters. It's preview technology, which means potentially breaking changes. Plus, you need to keep your Databricks extension files separate from your regular Azure Bicep files</p><p><strong>Terraform? We decided against it.</strong> Not because it's bad — it's excellent. But the operational overhead didn't justify the benefits for our specific situation. If we were multi-cloud or had a dedicated platform team, different story.</p><p>Here's the uncomfortable truth: there's no "best" tool. There's only the best tool for your situation <em>right now</em>.</p><p>We're still mostly using PowerShell because:</p><ul><li>The team knows it inside and out now</li><li>It's stable</li><li>No preview or GA concerns to worry about</li><li>It works with our existing workflows</li></ul><p>But I'm watching Bicep extensions closely. When they hit GA, when the tooling matures, when the separation concern gets addressed? We'll revisit. That's the real lesson: infrastructure decisions aren't permanent. They evolve as the tools evolve.</p><h2 id="the-tool-doesnt-matter-as-much-as-you-think">The tool doesn't matter as much as you think</h2><p>Six months ago, I thought choosing the right tool was everything. I read blog posts, watched YouTube talks, and debated in Teams channels.</p><p>Now I know better.</p><p>The best infrastructure code isn't the code written in the "best" tool. It's the code that your team actually maintains. It's the code that solves real problems. It's the code that ships.</p><p>These days, I spend less time debating tools and more time deploying infrastructure. I write Bicep templates for Databricks. When they don't work, I debug them. When they need to change, I change them. And you know what? It's boring. Which is exactly what infrastructure management should be.</p><p>Next up? I'm working on extending the Databricks Bicep extension with better examples and documentation. Because the real work isn't choosing tools — it's helping people actually use them.</p><p><strong>Want to try the Bicep Databricks extension?</strong> <a href="https://github.com/Gijsreyn/bicep-ext-databricks">Check out the documentation and examples on GitHub</a>.</p>
